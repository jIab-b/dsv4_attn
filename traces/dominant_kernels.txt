====================================================================================================
INTERPRETATION (what each role does in DSv4 decode)
====================================================================================================

TP_ALLREDUCE_CUSTOM        sglang's custom one-shot push-collective bf16 allreduce, fanout after
                           every TP-sharded matmul (attention out-proj, MoE expert outputs).
                           ~123k launches / 25s → ~4900 allreduces/sec at TP=4.

TP_ALLREDUCE_NCCL          stock NCCL RING_LL allreduce, used for smaller / less hot collectives
                           (some norms, lm_head shard).

MOE_GEMM_FP8FP4            deep_gemm sm100 FP8(act) x FP4(weight) → bf16 GEMM. The hot path for
                           routed-expert ffn: gate_up_proj + down_proj. Multiple shapes are
                           specialized (different M/N/K, group counts).

MOE_BMM / MOE_BMM_SWIGLU   Per-expert batched matmul kernels (CUDA-Q / TRT-LLM blockwise). The
                           swiGlu variants fuse activation. Used for grouped expert paths
                           that don't go through deep_gemm.

mHC_PRE / mHC_POST         Manifold-Constrained Hyper-Connection pre- and post-block kernels.
                           tilelang-generated. They project the residual stream onto the
                           manifold and project back, with a fused norm on the pre side.

mHC_PRENORM_GEMM           TF32 GEMM doing the H x C residual-mix matmul of mHC. Small but
                           per-layer per-token.

ATTN_MLA_SPARSE            FlashMLA decode kernel: split-K, FP8 e4m3 latent K + bf16 rope,
                           sparse top-k entry selection. Handles BOTH CSA layers (real
                           top-k) and HCA layers (all-entries dense, same kernel).

ATTN_SPLITK_COMBINE        Reduces split-K partials into final attention output (per-head O
                           and LSE). One per attention call. ← maps to your launch_hca_combine.

ATTN_TOPK_SCORE            paged_mqa_logits — computes scores to PICK the top-k compressed
                           KV entries (CSA-only path). Cheap because compressed entry count
                           is small.

ATTN_PLANNER               get_mla_metadata — produces split-K plan + per-request stride
                           tables. Runs once per batch (not per layer), so its absolute count
                           is low (~4k).

ATTN_KNORM_ROPE            fused_k_norm_rope_flashmla — RMSNorm on K plus RoPE in one kernel.
                           ← your sketch keeps these as separate steps; collapsing them is a
                           win you can replicate.

MOE_GATING                 moe_fused_gate_kernel_small_token — computes per-token expert top-k
                           routing scores.

MOE_ROUTING_IDX            routingIndicesDynBlockKernel — converts gate scores into the
                           per-expert token index buffers used by the grouped GEMMs.

MOE_FINALIZE               Sums expert outputs back into per-token vectors.

FP8_QUANT_PER_TOKEN        per_token_group_quant_8bit_kernel — bf16 → fp8 e4m3 with per-group
                           e8m0 microscale. Run before each FP8 GEMM input.

FP8_QUANT_BLOCK            TRT-LLM block-scale FP8 quantizer (variant used by flashinfer).

CUBLASLT_GEMM              nvjet_t{ss,st}_splitK_TNN — cuBLASLt GEMMs for non-MoE matmuls
                           (lm_head, attention proj fallbacks).

CUBLASLT_SPLITK_REDUCE     reduction half of cuBLASLt's split-K GEMM path.

ELEMENTWISE_COPY           Torch direct_copy_kernel (dtype casts in the residual stream).

INSTANCE-COUNT FINGERPRINT (what fired with what frequency):
  61,080 = SWA + (CSA-or-HCA per-layer attention) executions
  29,828 = CSA-only score/indexer pairs                 ~half of 61,080
  29,156 = "Compress4DecodeParams" dense paths          ~half of 61,080
  4,272  = MLA metadata planner (per-batch)
  1,420  = mHC head kernel (per-decode-step)
  1,396  = cuda graph launches (one per decode step, system-wide)

The 29k / 29k split is consistent with DSv4-Flash's CSA/HCA interleave: roughly half the
layers run the CSA top-k path (paged_mqa_logits + fused_q_indexer_rope_hadamard_quant)
and roughly half run the HCA dense path (flash_c4_decode). The 61k "sparse" kernel and
its associated norms+rope are the SHARED outer attention pass that both layer types do.

====================================================================================================
CONTEXT-LENGTH CAVEAT
====================================================================================================

This trace was captured at ~2.5-3 k tokens of context per request (server log:
'#full token: 2560'). That is well above HCA's m'=128 compression threshold so HCA had
real work to do, but it's far short of the long-context regime DSv4 was designed for.
At 1M tokens, HCA would attend to ~7,800 compressed entries and the c4_decode kernels
should grow from 0.3% to a much larger share. CSA's top-k path stays roughly flat in
relative cost because top-k is bounded.

A useful follow-up: rerun the same trace with a ~100 k-token prompt to surface HCA's
true workload character.

====================================================================================================
WHAT'S MISSING TO CLEANLY SEPARATE CSA vs HCA
====================================================================================================

The per-layer NVTX ranges sglang emits are generic ('layers.N', 'layers.N.self_attn') and
don't tag layer type. To attribute time cleanly to CSA-layers vs HCA-layers you'd need
one of:

  1. sglang source dive: read DeepseekV4ForCausalLM's layer list to know which N is which.
  2. Custom NVTX: wrap forward() of the CompressedSparseAttention and HeavilyCompressedAttention
     classes with explicit nvtx.range_push("CSA")/("HCA"), then re-run.
  3. Instance-count attribution: assume Compress4DecodeParams = HCA, SparseAttnDecodeParams = CSA,
     and split the 61,080 shared kernels by the ratio of their downstream-specific kernels.
     Rough enough but not authoritative.
