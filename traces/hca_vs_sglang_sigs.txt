HCA func-sig validation — your hca/params.h vs sglang's DSv4 decode kernels
====================================================================================================

Your `HcaParams` (in hca/params.h) is currently one big struct that fuses what sglang factors
across SIX distinct kernel-param structs at decode time. Below is the kernel-by-kernel mapping.
For each sglang kernel I quote the exact mangled sig as captured by nsys, then map every field
of `HcaParams` to where it lives in sglang. At the end: 3 concrete sig-level recommendations.

THE 3 CONCRETE SIG-LEVEL ISSUES TO FIX
====================================================================================================

1.  SPLIT HcaParams INTO TWO STRUCTS.
    Your single struct collapses two distinct kernels. Match sglang's factoring:
      struct HcaAttnDecodeParams {     // for kernel [B] — the attention reader
          // shapes:   B, M_cur[B], swa_len[B] (per-request, not int)
          // tensors:  Q, O, partial_O, partial_lse, attn_sink
          // cache descriptors: 9 TMA descriptors covering Kc / Kc_scales / Kc_rope /
          //                    Kswa / Kswa_scales / Kswa_rope / Q sw128 / Q sw64 / O
          // softmax:  sm_scale_log2
          // rope:     rope_theta_compressed, rope_theta_swa
      };
      struct HcaCompress128DecodeParams { // for kernel [A] — the per-step compressor
          // shapes:   B, m_prime=128, c_out=512 (both as compile-time template params)
          // inputs:   C, Z, bias / "ape"
          // state:    partial_count[B], M_cur[B] (per-request)
      };
    Your current HcaCombineParams is already the right shape for kernel [C], keep it.

2.  H IS WRONG (H=64 for V4-Flash, NOT 128).
    Your sketch and params.h both say H=128. The NVTX-captured `attn_sink: [64]` from
    the live model confirms H=64 for DSv4-Flash. Either:
      - keep H as a runtime int and accept a 2x increase in cycles for nothing
      - OR template the kernel on H (matches sglang: kernel template carries head config)
    V4-Pro uses H=128 → if you want one binary for both, H must be templated, not const.

3.  M_cur / swa_len / partial_count NEED TO BE PER-REQUEST.
    Your params.h has them as `int M_cur; int swa_len; int partial_count;` — that
    assumes every batch member has the same context length. sglang's
    SparseAttnDecodeParams takes `kv_indices : int*[B+1]` (CSR-style ragged) so requests
    in the same batch can be at different lengths. For real serving you need:
      int* M_cur;          // [B]
      int* swa_len;        // [B]
      int* partial_count;  // [B]
    or equivalent CSR-style page tables.

====================================================================================================
WHAT'S DIFFERENT AT THE KERNEL-FACTORING LEVEL (not sig issues, just info)
====================================================================================================

• sglang has NO separate "HCA dense" attention kernel.
  Both CSA-top-k attention and HCA-dense-over-compressed attention route through the
  same [B] flash_fwd_splitkv_mla_fp8_sparse_kernel. "sparse" = indexed-paged access,
  not selective compute. You CAN write a true-dense HCA kernel (no index list, contiguous
  access) — it'll be simpler and slightly faster per call, but you lose paging flexibility.

• sglang fuses K-norm+RoPE into one pre-pass [D] (fused_k_norm_rope_flashmla).
  Your sketch's Weights struct has normKc + per-step rope as separate ops. Fusing them
  matches sglang's perf — kernel-launch and bf16 read/write reduction are nontrivial.

• sglang's split-K is `num_splits=8` baked compile-time (the (int)8 in [C]).
  Your `num_splits` is runtime. If you template it you get a tighter register schedule.

• sglang's TMA descriptors live INSIDE the kernel template (TmaParams<...>), not in the
  param struct. This means the kernel is monomorphized per descriptor at JIT-compile
  time. Your params.h carries CUtensorMap by value — that works at runtime but the
  compiler can't optimize tile layouts as aggressively. Worth knowing.
