====================================================================================================
DSv4-Flash — per-context-length prefill + decode stats
4x B200, TP=4, sglang 0.5.12, --moe-runner-backend flashinfer_mxfp4
batch=1, temperature=0.7, top_p=0.9 (greedy crashes with NaN logits on this build)
====================================================================================================

INTENDED SWEEP: 50k, 100k, 150k, ..., 500k in 50k intervals.
ACTUAL OUTCOME: every long-context request triggers `Xid 31 MMU Fault: ENGINE GRAPHICS
                GPC*_GPCCLIENT_T1_* FAULT_PDE ACCESS_TYPE_VIRT_READ`. The TCP connection
                drops mid-stream, server dies, the next request hits ConnectionRefused.
                The fault occurs reliably from ~4k tokens upward on this exact build
                (sglang 0.5.12 / cu129 / FP4 MoE / 4x B200), so we cannot reach 500k.
                Restarting the server lets ONE more request through before the next fault.

We banked one partial measurement per server life (decoded a handful of tokens before the
fault was detected), then ran out of restarts. Below is everything we have, including the
earlier bench-loop data from the nsys traces (those used continuous bench-loops, so they
captured aggregate decode rates at batch>1).

====================================================================================================
WHAT THE NUMBERS SAY (with limited data)
====================================================================================================

PREFILL
  - Prefill throughput per request is roughly flat at ~4500-6000 tok/s in 8k-50k range
    (the 4k point's 637 tok/s is contaminated by first-request server startup; ignore it).
  - The 16k point hit 8,917 tok/s — almost certainly a partial radix-cache hit from a
    prior probe at the same prefix; treat as an outlier.
  - sglang's chunked-prefill (chunked_prefill_size=4096) means a 50k prompt is 13 chunks;
    server.log shows steady-state chunk throughput ~20-25k tok/s while in flight, but the
    end-to-end TTFT adds chunk-handover overhead + cudaGraph capture for the prefill batch.

DECODE
  - Per-request decode rate is **~135-175 tok/s** across all observed contexts (3k - 50k).
  - Per-request ms/decode-step is **~6-8 ms** across that range.
  - Decode rate at batch=1 is **strikingly flat** with context — but we couldn't push past
    50k to see HCA's cost cliff at 7800+ compressed entries. The bench-loop at batch=8
    over 3k context delivered ~127 tok/s/req at 0.97 ms/step, while batch=2 at 31k delivered
    142 tok/s/req at 3.52 ms/step. So per-step latency grew ~3.6x going from 3k → 31k context
    at batched load.

WHY ARE THE SINGLE-SHOT DECODE NUMBERS FLAT WHEN THE BENCH-LOOP NUMBERS GROW?
  - Single-shot at batch=1 is dominated by per-step overhead (TP allreduce launch latency,
    cudagraph launch, kernel-launch tail). Even at small context that's already 6 ms,
    which masks the linear attention-growth cost up to ~50k.
  - The bench-loop at batch>1 amortises the per-step overhead over multiple tokens per
    forward, so the attention compute term becomes visible. That's why the 3k -> 31k diff
    in batched load shows the 3.5x slowdown, but the single-shot sweep doesn't.

====================================================================================================
WHY THE CRASH (and what would unblock the 50k-500k sweep)
====================================================================================================

Failure signature (consistent across all post-warmup requests):
  Xid 31 NVRM MMU Fault: ENGINE GRAPHICS GPCx_GPCCLIENT_T1_y faulted @ 0x...
  Fault is of type FAULT_PDE ACCESS_TYPE_VIRT_READ

This is a GPU MMU saying a kernel issued a virtual-read against an unmapped page. It is
NOT a sglang Python-level bug; it's a kernel-side memory access violation. Most likely
culprit on this exact stack: the paged KV-cache index machinery (paged_mqa_logits +
flash_fwd_splitkv_mla_fp8_sparse_kernel) reading a page table entry the kernel believes
exists but the allocator hasn't mapped. Could also be:
  - cudagraph capture replaying with stale pointer (cuda graph + dynamic page table)
  - FP4 MoE dispatcher writing past expected buffer (deepep, mxfp4 backend)
  - NCCL custom-allreduce IPC handle expiring mid-graph (~448 cudaIpcOpenMemHandle calls
    per ~25s in the 3k trace — that's a recurring re-mapping)

Unblockers, in order of cheapness:
  1. Newer sglang. v0.5.12 is from before the post-launch DSv4 bugfix wave; the sglang
     issue tracker has open `Tracking DeepSeek V4 Flash GB200 serving fixes` (#23743).
     Try `lmsysorg/sglang:latest` or `v0.5.12-cu130` once it lands.
  2. Disable cudaGraph for the run (`--disable-cuda-graph`) — 5-10x slower decode but
     eliminates the graph-pointer-staleness hypothesis. Useful to confirm/refute the cause.
  3. Switch to V4-Pro on 8x B200 (or GB200) — sglang's Day-0 stability list shows V4-Pro
     is better-tested than V4-Flash, and the GB200 has different memory layout that
     dodges some of the V4-Flash B200 issues per #23743.
  4. Cap context at a known-stable point and use a smaller batch so per-token KV growth
     stays under whatever page-table size the kernel pre-allocates.
